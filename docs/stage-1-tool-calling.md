# Rust Harness 第一关：工具调用开发、测试与验收规范

> 状态：待实施、待实测  
> 适用范围：从零构建独立 Rust Harness 的第一关（Tool Calling）  
> 执行纪律：按顺序实施、逐项真实运行、逐关验收；第一关未通过，禁止开发第二关。

## 1. 建设目标

从零构建独立的 Rust 工具调用内核，验证真实大模型能否认识工具、自主选择工具、生成合法参数、实际调用工具，以及正确理解返回结果。

完整链路：

```text
工具注册 → 工具声明进入真实模型请求 → 模型识别与自主选择
         → 模型生成工具调用 → Rust 校验与执行
         → 工具结果按模型原生协议回填 → 模型理解结果
```

本阶段交付的是可靠、可运行、可诊断的工具调用测试内核及其测试证据，不是完整 Agent，不负责自动判断任务是否完成。

### 1.1 必须解决的历史问题

- 自定义工具已经开发，但模型不认识、不使用，或者错误地选择其他工具。
- Windows 原生程序及 PowerShell 在路径、参数、编码、超时和进程管理方面出现异常。
- 工具实际执行结果与模型获得的结果不一致，或者无法确定模型是否真的调用过工具。

### 1.2 范围边界

- 新项目独立于 MyBuddy，不依赖 Pi、Electron、Node.js 或已有 Agent 框架。
- 第一关只研究工具调用。允许测试所需的有限模型交互：首次模型请求、执行工具、工具结果回填及后续模型响应。不得借此提前开发通用 Agent Loop。
- 优先 Windows 原生运行；Linux 测试不能替代 Windows 实机验收。
- 首先选定一个实际支持原生工具调用的模型及供应商接口作为基线。其他模型后续单独对比，不要求第一关同时实现所有供应商。
- 模拟响应仅用于协议、边界和故障测试，不得代替真实模型的工具选择与结果理解测试。
- 不以提示模型指定工具、强制调用工具或替模型补全错误参数的方式冒充自主工具调用成功。

## 2. 执行顺序与阶段门禁

必须按以下顺序执行，每一步通过后才能进入下一步。若发现前置能力回归，回退至对应步骤修复并重新验收。

| 步骤 | 开发与验证内容 | 前置门禁 |
| --- | --- | --- |
| 1 | 真实模型接口连通及协议解析 | 无 |
| 2 | 单工具声明与识别 | 步骤 1 通过 |
| 3 | 单工具真实执行 | 步骤 2 通过 |
| 4 | 工具结果回填与理解 | 步骤 3 通过 |
| 5 | 多工具自主选择 | 步骤 4 通过 |
| 6 | Windows 原生文件工具 | 步骤 5 的基础选择用例通过 |
| 7 | 外部进程与 PowerShell | 步骤 6 通过 |
| 8 | 异常处理与边界测试 | 步骤 7 通过 |
| 9 | 第一关综合回归与验收 | 步骤 1–8 全部通过 |

各步骤的“通过”必须有实际运行证据，不允许仅凭源码审查、编译通过、模拟模型通过或模型自述判定成功。

## 3. 技术路线

| 项目 | 建议 |
| --- | --- |
| 核心语言 | Rust |
| 异步运行 | Tokio |
| HTTP 客户端 | reqwest |
| JSON | serde / serde_json |
| 参数校验 | JSON Schema，按实际供应商支持的子集生成声明 |
| 日志 | tracing |
| 测试 | Rust 原生测试框架、真实模型 CLI 测试入口 |
| 数据记录 | 本地 JSONL、测试报告及必要的原始协议证据 |
| 界面 | CLI |

先保持结构简单。模型接口适配、工具注册及执行、结果回填、测试与诊断应能独立测试，但无需在初期拆成大量 crate、服务或后台进程。

推荐逻辑模块：

```text
model       模型请求、流式/非流式响应解析、供应商协议适配
 tools      工具声明、注册、参数校验、真实执行
 platform   文件与进程的操作系统差异适配
 trace      请求、响应、调用与回填的关联记录
 tests      独立断言、协议夹具、真实模型及 Windows 测试入口
```

模型工具声明必须与实际执行接口一致。供应商特有的调用 ID、工具结果消息结构、流式分片和错误表示必须保留正确语义，不应为了统一接口而丢失必要字段。

## 4. 分步骤开发与验收

### 步骤 1：真实模型接口连通

开发内容：只建立最基本的模型通信、响应解析及诊断能力。

| ID | 测试场景 | 验收要求 |
| --- | --- | --- |
| M01 | 真实模型普通文本请求 | 正常获得模型回复，保存真实请求与响应 |
| M02 | 流式普通文本响应 | 分片正确拼接，无截断、重复或乱码 |
| M03 | 工具调用响应及参数分片 | 使用协议夹具解析完整调用，保留调用 ID、工具名及参数；不得在参数尚未完整时执行 |
| M04 | 供应商错误、限流、断开或截断 | 正确分类并返回错误，不冒充正常回复或工具成功 |

通过条件：真实模型普通对话连通；模型返回类型及协议解析的确定性测试全部通过。步骤 2–3 再实测真实模型工具调用分片。

### 步骤 2：单工具声明与识别

先实现无操作系统依赖的 `add_numbers`，用于隔离模型协议与平台执行问题。

建议 schema：两个整数输入，返回计算结果。参数类型、必填字段及范围必须明确。

| ID | 测试场景 | 验收要求 |
| --- | --- | --- |
| T01 | 注册工具并构造模型请求 | 检查实际发送的 tools 字段含正确名称、描述和 schema |
| T02 | 提示中明确提到工具名称 | 模型生成正确工具调用与合法参数，仅用于验证识别 |
| T03 | 供应商支持时强制指定工具 | 验证协议是否可用，独立统计，不计入自主选择指标 |
| T04 | 不提工具名的自然语言请求 | 使用允许模型自行选择工具的配置，观察模型是否主动调用 |
| T05 | 不需要工具的普通问题 | 模型应可正常直接回复，不强制工具调用 |

注意：简单加法可能由模型直接计算，这不一定是能力错误。T04 的正式自主选择验收应使用明确要求实际工具计算或依赖运行时数据的任务；不得把无需调用工具也能正确回答的算术问题当成必须调用的用例。

通过条件：工具声明的实际传递及明确调用测试通过；自然选择的基础测试具有实际调用证据。若未调用，先记录并归因，不增加复杂工具系统掩盖问题。

### 步骤 3：单工具真实调用

建立最小工具注册表及执行器：名称查找、参数解析与校验、调用执行及结果返回。

| ID | 测试场景 | 验收要求 |
| --- | --- | --- |
| E01 | 正数、零、负数计算 | Rust 真实执行，独立断言结果正确 |
| E02 | 非法类型、缺失字段、越界参数 | 明确拒绝，不执行、不隐式编造参数 |
| E03 | 未注册工具 | 明确返回未知工具错误 |
| E04 | 真实模型调用 | 原始模型调用正确映射至工具函数，执行记录可核对 |
| E05 | 真实模型流式工具调用（接口支持时） | 完整接收参数后执行，不提前或重复执行 |

通过条件：所有确定性断言 100% 通过；至少有真实模型产生的调用被 Rust 实际执行成功。模型自行计算的文本不计为工具执行成功。

### 步骤 4：工具结果回填与理解

新增 `generate_nonce`：Rust 在执行时生成随机字符串，值对模型事先不可知。使用独立测试程序核对模型最终回复是否精确包含该随机值。

固定测试交互：

```text
首次真实模型请求（含工具声明）
→ 收到工具调用
→ Rust 真实执行工具并生成随机值
→ 保存 assistant 工具调用消息
→ 按供应商协议回填匹配调用 ID 的工具结果
→ 请求模型读取结果并回答
→ 外部断言对比随机值
```

这一交互仅是固定测试夹具。若模型产生额外工具调用，应记录实际行为，不通过无限循环来完成测试；通用循环控制留待第二关。

| ID | 测试场景 | 验收要求 |
| --- | --- | --- |
| R01 | 单次 nonce 调用 | 模型返回精确值，匹配 Rust 实际生成的随机值 |
| R02 | 结构化工具结果 | 模型能正确读取字段及其含义 |
| R03 | 工具失败结果回填 | 模型可识别失败，不应报告虚假成功 |
| R04 | 多个调用结果的关联（接口支持时） | 每个结果与对应调用 ID 正确匹配 |
| R05 | 缺失或错误关联 ID（协议夹具） | 被检测并返回明确协议错误 |

通过条件：结果回填及调用关联的确定性测试全部通过；真实模型 nonce 及结构化结果测试达到模型行为标准。

### 步骤 5：多工具自主选择

在不改变模型版本、主要提示词与测试任务的前提下，逐步增加工具数量。

| 工具数量 | 用途 | 门禁性质 |
| --- | --- | --- |
| 1 | 基本工具识别 | 基础门禁 |
| 3 | 基本竞争与选择 | 基础门禁 |
| 5 | 不同能力之间的选择 | 基础门禁 |
| 10 | 相似工具竞争 | 基础门禁 |
| 20 | 工具规模扩大后的选择变化 | 压力测试，必须记录结果 |
| 50 | 工具规模压力及退化分析 | 压力测试，必须记录结果；若超出供应商限制，记录限制 |

测试集合必须覆盖：功能不同、功能相近、名称相近、描述不同、不需要工具的任务。测试工具可以包含无副作用的合成工具，但每个工具的声明必须真实对应可执行实现；不得使用无法执行的虚假工具作为正式通过证据。

测试方法：

- 自主选择测试不提示具体工具名称、不强制 tool choice，不额外告诉模型正确答案。
- 在测试前定义正确工具或可接受的工具集合、参数断言及结果断言；多个合法解法不能事后任意判错。
- 记录每次调用中模型实际看到的工具集合、名称、描述、schema 及模型配置。
- 比较工具描述优化前后的结果时，固定其他变量；保留失败样例及对照实验记录。
- 步骤 6–7 的实际工具完成后，必须再次执行真实工具集合下的自主选择专项回归，不能只靠合成工具证明实用性。

通过条件：基础规模达到第 5 节模型行为验收标准，压力规模单独报告退化、失败原因及适用边界。若实际产品要求一次暴露 20 或 50 个工具，该规模必须另设正式门禁后才能宣称支持。

### 步骤 6：Windows 原生文件工具

先采用 Rust 文件系统 API 及必要的原生库实现，不通过 PowerShell 间接完成基础文件操作。

| 工具 | 职责 |
| --- | --- |
| `list_files` | 列出目录及文件 |
| `read_file` | 按明确范围读取文件内容 |
| `write_file` | 按约定创建或写入文件 |
| `search_text` | 搜索文件文本，返回路径及位置 |
| `apply_patch` | 对文件执行受控局部修改 |
| `file_info` | 返回明确的文件属性 |

各工具必须先通过独立 Rust 测试，再加入模型实际工具集合进行自然语言测试。

| ID | 测试场景 | 验收要求 |
| --- | --- | --- |
| W01 | 中文目录、中文文件名 | 路径正确识别和访问 |
| W02 | 含空格路径 | 不错误拆分，不依赖模型手工加引号 |
| W03 | 相对路径、绝对路径、工作目录 | 解析符合已声明规则 |
| W04 | 长路径 | 在系统支持条件下正确处理；不支持时明确报告 |
| W05 | UTF-8、带 BOM、CRLF | 按声明的编码与换行规则读取、修改，不破坏内容 |
| W06 | 文件不存在、权限不足、文件占用 | 返回真实错误，区分错误类型 |
| W07 | 局部修改 | 外部测试检查修改内容及未修改区域，失败不得报告成功 |
| W08 | 模型自主选择 | 不提示工具名，模型选择合适原生工具并完成实际操作 |

测试限定在专用临时工作目录，不修改真实业务文件。路径越界、符号链接或重解析点必须符合明确的测试工作区访问策略；不支持的情况应清楚报错。

通过条件：Windows 原生实机的确定性断言全部通过；实际模型工具选择、参数生成、结果理解达到第 5 节标准。

### 步骤 7：外部进程与 PowerShell

实现两个职责不同的工具，不把所有动作都交给 Shell。

#### 7.1 `run_process`

用于直接运行外部程序。结构化参数至少包含程序名或路径、参数数组、工作目录、必要环境变量及超时。不得把参数简单拼成一条 shell 命令。

Windows 批处理、`cmd.exe` 等具有特殊参数解释的程序应明确支持策略，不得假设所有程序遵循相同解析规则。

#### 7.2 `run_shell`

用于需要 Shell 解释的脚本、管道、PowerShell cmdlet。明确指定 shell 类型、版本、脚本、工作目录、输出及超时语义。PowerShell 5.1 与 PowerShell 7 分别实测，不得混用通过结果。

#### 7.3 专项验收

| ID | 测试场景 | 验收要求 |
| --- | --- | --- |
| P01 | Git、Cargo 等原生程序 | 已安装时能真实启动并取得输出及退出码 |
| P02 | 中文、空格、空参数 | 使用受控参数回显程序独立核对 argv |
| P03 | 单双引号、反斜杠、JSON 参数 | 参数与预期一致，不被二次解释 |
| P04 | 特定 cwd 与 env | 子进程正确获得独立工作目录及环境变量 |
| P05 | PowerShell 多行脚本、管道、cmdlet | 在 5.1 与 7 分别执行并核对真实结果 |
| P06 | 非零退出码、程序不存在 | 正确区分启动失败与运行失败 |
| P07 | 大量 stdout、stderr | 两路输出持续消费，无死锁，截断有标识 |
| P08 | 长时间运行及超时 | 不无限等待；正确记录是否启动、结束、超时 |
| P09 | 取消及受控子进程树 | 验证取消后受控进程及子进程被清理；清理失败必须明确报告 |
| P10 | 模型自然选择 | 根据任务选择文件工具、直接进程或 shell，并由独立断言确认结果 |

第一关只需提供受控进程执行及明确的完成、失败、超时、取消结果。若提供异步进程句柄，必须明确区分“已启动”和“已结束”，但不因此开发后台任务系统。

通过条件：Windows 上真实执行的确定性测试 100% 通过；实际工具选择达到模型行为标准。目标环境未安装某个必须验收的 PowerShell 版本或程序时，记为 BLOCKED，不得用另一个版本、模拟结果或 Linux 替代。

### 步骤 8：异常处理与边界测试

| ID | 测试场景 | 验收要求 |
| --- | --- | --- |
| X01 | 未知工具、错误参数、无效 JSON | 明确分类，非法输入不能触发实际执行 |
| X02 | 缺失、重复或不匹配的调用 ID | 检测协议问题，重复交付的同一调用不得造成重复副作用 |
| X03 | 多工具调用（接口支持时） | 各调用独立关联结果；第一关不要求并行调度，可串行执行 |
| X04 | 工具执行失败 | 错误准确回填，无虚假成功 |
| X05 | 网络中断、模型响应截断 | 不执行未完整的调用，不伪造结果 |
| X06 | 工具超时、取消 | 返回明确状态，受控执行资源正确清理 |
| X07 | 副作用发生后结果丢失 | 不自动重放非幂等动作；明确报告结果未知及可用证据 |
| X08 | 输出过大、日志脱敏 | 输出限制有效，保留截断标识；不泄露密钥或敏感内容 |

不要求实现复杂重试、持久化恢复、任务调度或业务完成判断。所有测试必须有独立断言，不能仅凭程序没有崩溃判定通过。

### 步骤 9：综合回归

用完整的实际工具集合运行真实模型测试，包含以下相互独立的场景：

- 不使用工具即可回答的普通问题。
- 读取只有测试文件中存在的随机信息。
- 搜索真实文件中的随机标记，返回路径和匹配位置。
- 修改专用测试文件，由外部程序验证文件变化。
- 获取外部程序输出中的随机值，由外部断言核对。
- 使用确实需要 PowerShell 的 cmdlet 完成一个无副作用操作。
- 工具执行失败时准确反映失败结果。

每个场景使用第一关限定的测试交互，验证工具识别、选择、执行、回填与理解。不得把这些用例扩展成第二关的开放式多轮任务完成测试。

综合回归须覆盖全部前置步骤。修改核心协议、schema、工具描述或执行层后，应重新运行受影响的专项及综合回归。

## 5. 测试指标与统计口径

### 5.1 确定性程序指标

| 指标 | 最终门禁 |
| --- | ---: |
| 工具注册正确率 | 100% |
| 工具声明实际传递正确率 | 100% |
| 合法参数解析正确率 | 100% |
| 非法参数拒绝正确率 | 100% |
| 合法工具执行与独立断言一致率 | 100% |
| 工具结果回填正确率 | 100% |
| 调用 ID 关联正确率 | 100% |
| Windows 原生专项确定性断言 | 100% |

100% 指已定义且实际执行的测试集全部通过，不代表所有现实输入都无缺陷。缺失、跳过或阻塞的必测用例不得计入通过。

### 5.2 真实模型行为指标

| 指标 | 建议初始正式门禁 |
| --- | ---: |
| 自主工具选择正确率 | ≥95% |
| 模型参数生成正确率 | ≥95% |
| 模型结果理解正确率 | ≥95% |

正式验收建议每类至少 100 次独立测试，采用多种自然语言表达及测试数据，而不是重复完全相同的问题。开发过程中允许先做少量冒烟测试，不能用冒烟结果代替正式验收。

- 自主选择正确率 = 选中预定义可接受工具（或正确选择不调用）的任务数 / 对应有效自主选择任务数。
- 参数生成正确率 = 正确工具调用中参数满足 schema 及任务语义的调用数 / 对应正确工具调用数。
- 结果理解正确率 = 正确回填结果后、最终回答符合独立断言的任务数 / 对应结果理解任务数。
- 同时报告端到端成功率 = 工具选择、参数、执行、回填、理解全部满足断言的任务数 / 所有预定有效任务数，避免条件成功率掩盖前序失败。暂不另设端到端数值门槛，但必须如实披露并分析与分项指标的差异。
- 强制工具、明确提示工具名、模拟模型与自主选择结果分别统计。
- 按模型、供应商、模型版本、工具规模及测试类别分组。不同模型的结果不得混合形成总体通过率。
- 正式报告同时列出计划数、实际尝试数、有效数、失败数、阻塞数及排除原因。供应商中断、限流等可另行归类，但不得删除记录来提高成功率。预定有效样本不足时，不得宣布正式门禁通过。
- 记录首次尝试结果。修复后回归另建测试批次，不得覆盖历史失败。

以上 95% 和样本数为初始工程建议，不是已知模型实测能力。正式执行前固定门禁口径；如需调整，必须注明依据并得到项目负责人确认，不得为了通过测试事后降低标准。

### 5.3 失败归因

失败必须尽可能归入具体环节：工具未进入模型请求、schema 或描述问题、模型选错/不选、模型参数问题、协议解析错误、原生执行错误、平台适配错误、结果回填错误、模型结果理解错误、供应商/网络错误或待定位。

不得把所有失败都归因于模型，也不得把所有模型行为差异都归因于 Rust。证据不足时标记待定位。

## 6. 诊断与验收证据

每次测试至少记录：

| 字段 | 说明 |
| --- | --- |
| `test_id` / `attempt_id` | 测试用例及独立尝试标识 |
| 模型及配置 | 供应商、模型名称或版本、采样设置、工具选择配置 |
| 运行环境 | 操作系统版本、Rust 版本、PowerShell 版本（适用时）、代码提交号 |
| 实际模型请求 | 工具定义、消息结构、发送时间及可关联请求标识 |
| 模型原始响应 | 响应类型、工具调用名称/ID、原始参数及必要的流式记录 |
| 工具执行 | 校验结果、解析参数、执行时间、状态、结果及错误 |
| 结果回填 | 实际提交给模型的工具结果及对应调用 ID |
| 最终输出 | 模型实际返回的答案 |
| 独立断言 | 预期值、实际值、断言结果及证据位置 |
| 判定 | PASS / FAIL / BLOCKED / NOT_RUN，失败分类及原因 |

日志应关联同一次测试的请求、调用、执行及回填，使用本地 JSONL 等易检查格式。必须脱敏 API Key、授权头、环境变量中的密钥及敏感文件内容。保留足够诊断语义，不要求输出模型未公开的内部推理。

## 7. 本阶段明确禁止事项

- 不开发 Planner、Verifier、Reviewer、Supervisor 或多模型审查机制。
- 不开发强制“执行 → 验证 → 交付 → 结束”的业务状态机。
- 不开发通用 Agent Loop、自主任务完成判断、无限自检治理机制。
- 不开发记忆、上下文压缩、子代理、任务委派、MCP、Skills、Gadgets。
- 不开发后台调度、Cron、持续监控、复杂工具动态发现框架。
- 不引入 GUI、Electron、Node.js、数据库或不必要的独立服务。
- 不为通过测试硬编码模型答案、伪造调用、替模型自动选择工具或隐藏失败记录。
- 不修改 MyBuddy，也不将其既有功能迁移到新项目作为第一关的前提。

工具执行的参数校验、超时、取消、输出限制等必要基础设施不属于第二关，应在第一关完成。

## 8. 第一关交付物

1. 可独立运行的 Rust CLI 工程及源码，包含真实模型接口与工具调用测试入口。
2. 可重复执行的 Rust 确定性测试及真实模型测试集合，测试运行命令、依赖、配置及环境准备说明。

4. 脱敏后的模型请求、响应、工具调用、结果回填与独立断言记录。
5. 按模型和工具规模划分的统计报告、失败样例及归因记录。
6. 第一关最终验收报告，明确通过、失败、阻塞及未测项目。

本规划不指定仓库名称、真实模型供应商或 API 密钥；这些由实际实施环境确定并写入测试报告。模型账号、网络或实机不可用时，允许完成本地可测项目，但真实模型或 Windows 门禁保持 BLOCKED，不得宣称第一关验收通过。
