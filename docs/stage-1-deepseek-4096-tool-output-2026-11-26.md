# SourceHarness 工具返回实验：DeepSeek 4K 基线与格式对照

日期：2026-11-26。代码参考：`f2a139d`。实测主机：Windows（vivion）。模型路由：`opencode-go/deepseek-v4.1-flash`，通过本机 Magpie 连接。两轮均使用 4 个并发请求，每个请求显式设置 `max_tokens: 4096`，并保存请求核对实际参数。这是独立的实验脚本，不代表 Rust CLI 的默认输出上限发生变化。

## 目的与输入

要回答的是：**工具返回哪些事实，用什么格式，能让模型以更少的上下文做对下一步？** 这不是逐字复述测试，也不是真实业务工具的端到端验收。

每道题构造一段固定历史：用户任务 → 模拟的上一条工具调用 → 与同一 `tool_call_id` 关联的合成工具结果。将这段历史和工具声明发送到兼容 Chat Completions 的接口（非流式，`tool_choice: auto`），实际读取模型发出的下一条动作。题目仅使用合成数据，未执行生成的工具调用，没有真实搜索、文件读写、服务重试或权限变更。

### 复跑步骤

1. **千题基线：**准备下表十类合成场景各 100 题。替换编号、分隔符、候选记录、目标顺序和中英文文本，保留每题唯一编号及预期工具名、类型与参数，或预期停止条件。随机化发出顺序，最多 4 路在途。
2. **格式对照：**另取 96 道新题，搜索和缺参各 48 道。每题复制成四臂，只改最后的工具结果正文；模型、工具声明、上一轮调用、用户指令和正确答案不变。四臂随机交错发出：原版紧凑 JSON、同事实短文本、加一条事实的紧凑 JSON、同事实短文本。短文本使用换行分隔的 `key=value`。
3. **打分：**该调用时要求恰好一次调用、新调用 ID、正确工具名和值及类型完全匹配的参数，参数不得重复或多出，结束原因应为 `tool_calls`。该停止时要求无调用、结束原因为 `stop`、有正文且表达核心结果。千题通过了 398 道停止题：392 道通过规则筛查，6 道规则外例逐条复核；对已通过筛查的正文仅做抽查，未逐字审核。
4. **落盘与恢复：**保存题号、试验臂、请求和结果。HTTP/传输失败单独统计，补测不能覆盖首轮证据。Windows 格式对照长会话曾中断，后以四路并发、短批次续跑，跳过已保留的题号／试验臂；最终核对四臂都包含同一批 96 题、384 条全部有效且没有重复。仓库保留逐条计分记录，不包含原始请求或响应正文、供应商响应 ID、凭据或本地目录。
5. **统计：**按场景及试验臂计算通过数。格式对照以题号配对，分开统计从错到对、从对到错。Token 以上游 usage 为准，包含整个请求和模型生成，不是只计工具结果字段长度。每请求耗时包含本地网关和上游往返，不含中断间隔。

### 两个对照示例

| 场景 | 原版紧凑 JSON | 只增加的事实 | 应发出的动作 |
|---|---|---|---|
| 档案编号 `SENSOR-258-QA-lot7` 未找到，用户要求查同组 | `{"status":"ok","data":{"found":false}}` | 在 `data` 增加 `"family_prefix":"SENSOR-258-QA-"` | 只发一次 `find_family(prefix="SENSOR-258-QA-")` |
| 自动查找缺少记录键，用户已给记录键及订单号 | `{"status":"error","code":"MISSING_ARGUMENT","field":"record_key"}` | 增加 `"recovery_tool":"lookup_by_record_key"` | 使用给定记录键调用 `lookup_by_record_key`，而非再调用自动查找 |

例如搜索增强短文本为：

```text
status=ok
found=false
family_prefix=SENSOR-258-QA-
```

## 千题基线

**990/1,000（99.0%）**。该调用 592/600，该停止 398/400。1,000 条均 HTTP 200，无限流、超时或补测。总历时 19 分 25 秒；单请求 P50 2.11 秒、P95 21.18 秒。输入 486,170 Token，输出 119,685 Token；单题输出最高 493 Token，没有触及 4K，也没有达到 512。这不是 512 与 4096 的同题对照。

| 场景 | 通过 | 预期动作 |
|---|---:|---|
| 搜索同组 | 95/100 | 使用准确前缀且只查一次 |
| 游标翻页 | 100/100 | 抄对目标记录的游标 |
| 字节偏移翻页 | 100/100 | 使用目标输出引用和正确字节偏移 |
| 已知参数补齐 | 97/100 | 选择对应工具，填对给定标识 |
| 可安全重试 | 100/100 | 按指定等待时间安排一次模拟重查 |
| 执行状态未知 | 100/100 | 查询原操作，不重复执行 |
| 用户禁止重试 | 100/100 | 只报告，停止 |
| 缺参且用户未提供 | 100/100 | 询问缺失的键，不猜值调用 |
| 权限拒绝 | 100/100 | 报告拒绝，不绕行 |
| 精确查询无命中 | 98/100 | 报告无命中，停止 |

错题：5 道搜索用了过宽前缀（其中 4 道同时发了另一条调用），3 道补参题选错工具或多问了一次，2 道精确查询无命中后又发起调用。

## 96 题同题四臂对照

384 条均 HTTP 200，无记录到限流或超时。下面的耗时是单请求耗时，不是把分批恢复期间的空档算进模型速度。

| 试验臂 | 搜索 | 缺参 | 合计 | 平均输入 / 输出 Token | P50 / P95 |
|---|---:|---:|---:|---:|---:|
| 原版 JSON | 46/48 | 47/48 | 93/96 | 472.4 / 160.6 | 2.48 / 5.28 秒 |
| 原版短文本 | 48/48 | 47/48 | 95/96 | 468.9 / 143.7 | 2.39 / 8.12 秒 |
| 加字段 JSON | 48/48 | 48/48 | 96/96 | 486.8 / 117.0 | 2.16 / 4.63 秒 |
| 加字段短文本 | 48/48 | 48/48 | 96/96 | 483.0 / 118.7 | 2.16 / 3.47 秒 |

- 固定原版事实，JSON 换短文本：3 题从错到对、1 题从对到错。固定增强事实，两种格式均通过全部 96 题。数据不足以判断哪种格式更准，或推断普遍延迟差。
- 固定 JSON，加字段挽回 3 题（搜索 2、缺参 1），无退化；固定短文本，加字段挽回 1 道缺参题，无退化。增强 JSON 平均总用量从 633 降到 604 Token；增强短文本约 602 Token。此次多给字段增加了输入，但生成 Token 减少。
- 只覆盖两类合成题及一个模型的单次运行，观察到的提升不代表其他任务、模型或真工具同样提高。

## 建议

默认用紧凑 JSON，保留能改变下一步动作的字段，而不是增加通用说明。只有工具确实知道同组范围时才返回 `family_prefix`；只有注册表能唯一确定恢复工具时才返回 `recovery_tool`。这些是事实或可选恢复信息，不给模型新增授权，也不替模型决定下一步。原始调试信息留在本地。本提交不改工具运行时、提示词或 CLI 默认值。
